Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows how the components interact with each other for the scenario where the user issues the command delete 1.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • displays the exact command submitted by the user above its success or error feedback in the ResultDisplay.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Logic component

API : Logic.java

Here's a (partial) class diagram of the Logic component:

The sequence diagram below illustrates the interactions within the Logic component, taking an add command as an example.

Note: The lifeline for AddCommandParser should end at the destroy marker (X), but due to a limitation of PlantUML, the lifeline continues till the end of diagram.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a ClientBookParser object, which in turn creates a parser that matches the command (e.g., AddCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., AddCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to add a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

LogicManager executes each command against a temporary model initialized with the current records, preferences and active filter. When a command changes records, it saves the temporary client book before committing it to the main model. Read-only commands, such as list, find, and due, update the displayed view from memory without writing to storage. If saving fails, the main model is never committed, so the application does not display a change that would be lost after restart. Regression tests cover read-only commands avoiding persistence, a failed save retaining the records and active filter, and a subsequent successful tag command preserving that filter.

Model component

API : Model.java

The Model component,

  • stores the client book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • retains the complete list as the source of displayed indexes. Filtering and editing do not change a person's index; deleting a person removes it from the source list and renumbers the persons after it.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in ClientBook, and each Person references tags from that list. This lets ClientBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both client book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonClientBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Find by name, relationship, tags and remembered details

The find command supports four independently optional filters: name keywords, one relationship, tag keywords, and remembered-detail keywords. FindCommandParser tokenizes the r/, t/, and k/ prefixes, rejects duplicate filter prefixes, and delegates relationship and tag validation to ParserUtil. At least one filter must be present. Name keywords precede the prefixed filters; multiple tag or detail keywords follow one corresponding prefix and are separated by whitespace. The parser splits the name preamble into independent keywords and validates each one against the search-keyword grammar. Ordinary name keywords contain letters with optional internal hyphens or apostrophes, while s/o, d/o, and w/o are also valid standalone keywords. Digits, other symbols, and arbitrary slash forms are rejected for names. Detail keywords accept any non-whitespace text so users can search remembered values such as times, dates, and punctuation.

The parser creates a PersonMatchesFiltersPredicate. Name keywords use case-insensitive contiguous substring matching and are joined with OR. Thus, Alex matches Alexander, while either Anne or Marie matches Anne-Marie Tan. Tag keywords use the same case-insensitive contiguous substring matching and are also joined with OR; for example, friend matches both friend and friends. Detail keywords search the two contact preferences, the three financial-information fields, each interaction note's date and text, and the follow-up action text and due date. Dates use their ISO yyyy-MM-dd representation, so both full dates and contiguous fragments match. Follow-up completion status is excluded. Detail keywords are joined with OR. The predicate joins the name, relationship, tag, and detail filter results with AND. For example, find Alex David r/client t/priority referral k/retirement WhatsApp returns clients whose name contains Alex or David, whose tags contain priority or referral, and whose remembered details contain retirement or WhatsApp.

FindCommand passes the predicate to Model#updateFilteredPersonList(Predicate<Person>), which updates the FilteredList<Person> observed by the UI. Filtering does not reorder the source list, so matching persons retain the same order and indexes as in the list command. PersonListPanel looks up each filtered person in the complete list when rendering its index. Index-based commands use Command#getVisiblePersonAtIndex to resolve that complete-list index and reject it if the corresponding person is not in the current filter.

The successful CommandResult returned by FindCommand includes a selection request. MainWindow responds by calling PersonListPanel#selectFirstPerson, which selects the first filtered person and scrolls it into view, or clears the selection if the result list is empty. A key-event filter on MainWindow handles the Up and Down arrow keys whenever a person is selected. It asks PersonListPanel to select the previous or next result and scroll to that index. Selection remains at the corresponding boundary when the first or last result is reached. Keeping this navigation at the window level allows it to work while the command box retains keyboard focus.

Tagging a person

TagCommandParser reads the first whitespace-separated argument as the displayed-list index and validates each remaining argument with ParserUtil#parseTags(Collection<String>). Tag names use the existing alphanumeric-only Tag validation. TagCommand resolves the visible person against its index in the complete list using Command#getVisiblePersonAtIndex. It then intersects the supplied and existing tag sets. Tag equality is case-insensitive, so a non-empty intersection raises a CommandException listing the duplicate tags and leaves the contact unchanged. Otherwise, the command unions the supplied and existing tags and replaces the immutable Person through Model#setPerson, preserving every non-tag field and the active list filter. The existing JSON adapter persists a successfully updated set.

AddCommandParser uses the same validation and accepts zero or more t/TAG fields. Unlike the required name, relationship, email and phone prefixes, t/ is deliberately repeatable so a new person can be created with several tags. The parser collects those values into a set before constructing the Person.

PersonCard renders the complete tag set in its existing FlowPane, sorting tags by name for deterministic display. The list view observes the model, so tags supplied by add or appended by tag appear with the person's contact and relationship details without a manual refresh. The list command restores all persons while retaining those tags.

The following sequence shows tags being appended to a person in the currently displayed list. Parsing and index validation complete before the immutable Person is replaced and the updated client book is saved.

Deleting tags from a person

TagDeleteCommandParser reads the displayed-list index and an optional set of tag names. An empty set means all tags; otherwise, TagDeleteCommand requires every supplied tag to exist on the person. Matching uses the same case-insensitive Tag equality as tag addition. Missing tags, a person with no tags, or an invalid displayed index raises a CommandException before confirmation or mutation.

Tag deletion uses a two-phase Logic flow. The initial Logic#execute(String) call parses and validates the command, stores the pending TagDeleteCommand, and returns a CommandResult containing Are you sure you want to delete this?, the contact name, the exact stored tags that will be removed, and the accepted responses. MainWindow displays the result through the existing result box below the command box.

While a deletion is pending, LogicManager interprets the next command-box input as a confirmation response instead of parsing it as a new command. y and yes execute the stored command; n and no discard it. Matching is case-insensitive and ignores surrounding whitespace. Any other response raises a CommandException and leaves the command pending. A confirmed command copies the person's tag set, clears it or removes the selected tags, replaces the immutable Person through Model#setPerson, and saves the updated client book.

Contact preferences (US12)

ContactCommandParser accepts contact INDEX [ch/CHANNEL|-] [tm/TIMING|-] in either prefix order. It reuses duplicate-prefix checks and ParserUtil.parseIndex, but retains raw preference values using the same ordinary-space prefix boundaries as ArgumentTokenizer. ClientBookParser passes the original contact arguments so its initial trimming cannot change marker recognition. The shared tokenizer is unchanged.

Only an exact - surrounded by ordinary spaces clears a preference. Non-marker values retain the existing trimming and validation through immutable PreferredContactChannel and PreferredContactTiming. Thus a tab-padded hyphen is normal text, not a clear operation. Free text, Unicode, punctuation and the 1-200-character limit remain supported.

ContactDescriptor holds a specified flag and nullable value for each preference: omitted means preserve, specified non-null means replace, and specified null means clear. ContactCommand defensively copies the descriptor and rejects an empty descriptor. It calls Command#getVisiblePersonAtIndex to resolve the original full-list index and verify that the person is visible in the current filtered results. Search results retain their original indices, matching the numbers shown by the UI. It then constructs a replacement Person with the resolved preferences and calls Model#setPerson. Person#withContactPreferences retains its original null-means-keep contract for other callers. All unrelated fields and the active filter are preserved. edit, info, note, withNextAction and PersonBuilder also copy both preferences. PersonCard hides absent values and wraps recorded values. JsonAdaptedPerson persists optional preferredContactChannel and preferredContactTiming strings; missing or null properties mean absence, while invalid non-null values produce IllegalValueException. Clearing uses this existing absence representation without changing the JSON format. Clearing absent fields and repeating clears are safe. Tests cover set/clear combinations, raw markers, invalid-input atomicity, filtered indices, unrelated-field preservation, descriptor equality/copying, JSON save/reload after clearing, and live card label hiding.

Financial information (US13)

FinancialNeed, Priority and AreaOfInterest are immutable value objects, independently optional on Person. Normal values contain 1-200 characters after trimming ordinary spaces; internal spaces are preserved. Validation accepts Unicode letters (\p{L}), combining marks (\p{M}), decimal digits, spaces and the punctuation . , ' ( ) & - $ % + /; blanks, tabs, line breaks and other characters are rejected. Combining marks support decomposed accents and scripts such as Tamil. No Unicode normalization is performed: stored text and equality retain the supplied representation after ordinary-space trimming. The existing 200-character limit uses String.length() (UTF-16 code units), including combining marks. Priority stores validated text rather than a fixed enumeration.

ClientBookParser routes info INDEX [fn/VALUE|-] [pr/VALUE|-] [ai/VALUE|-] to InfoCommandParser. The parser requires a positive index and at least one financial prefix, accepts any prefix order, and rejects duplicates. A prefix starts only at the beginning of the arguments or after whitespace. The local scanner reserves only fn/, pr/, ai/, their case variants, and the explicit near misses fnn/, prr/, aii/ (also case-insensitive). Only the three exact lowercase prefixes are valid; the other reserved forms report an invalid parameter. This deliberately small reservation avoids a broad edit-distance or generic NAME/ heuristic that would reject ordinary financial text. For example, fn/Planning CPF/SRS, fn/Save $3000/month, ai/Planning Life/Health insurance, and fn/ CPF/SRS preserve their complete values. Slash-first tokens (including legacy /fn, /pr, /ai and a bare /) still produce the invalid-parameter diagnostic. No shared tokenizer changes are needed.

A separate scan of the preamble rejects any unknown NAME/ token before the first field: value text cannot occur there. The preceding index is validated first, preserving invalid-index diagnostics. Inside a field, unknown forms such as xyz/Value, fna/Value, or fnValue/Value are ordinary value text, subject to the usual character and length validation. They cannot reliably be distinguished from CPF/SRS or $3000/month. The explicit near-miss reservations above also cannot be used literally at token boundaries within values; users must rephrase them. Recognised prefixes and slash-first tokens retain their existing scan precedence over index validation. Parser, command atomicity, and save/reload regression tests cover these rules.

There is an unavoidable ambiguity between a new parameter and literal prefix-like text within free text: fn/Review pr/High options sets financial need to Review and priority to High options. Every whitespace-delimited known prefix starts a field; duplicate prefixes fail. Quoting and escaping are not supported, so users must rephrase literal prefix-like text. This restriction is also in the User Guide and covered by parser regression tests. Attached fn/pr/High stores literal pr/High as financial need.

The parser recognizes an exact - surrounded only by ordinary spaces before calling ParserUtil to validate normal values. Bare prefixes remain invalid. InfoDescriptor stores a specified flag and nullable value per field: omitted means unchanged, specified non-null means replace, and specified null means explicitly clear. InfoCommand defensively copies this descriptor, including its flags.

InfoCommand#execute resolves the visible person against its index in the complete list before mutation. It constructs a replacement Person using the resolved financial fields and calls Model#setPerson. Name, phone, email, relationship, tags, interaction notes, next action, preferred contact channel and preferred contact timing are copied unchanged; the active filter is preserved. Clearing an absent field is idempotent.

LogicManager saves through the existing storage pipeline after execution. JsonAdaptedPerson persists optional financialNeed, priority and areaOfInterest strings; missing or null properties load as absent, supporting older files. Non-null values are validated on loading. PersonCard shows present values in wrapped labels prefixed with Financial need:, Priority: and Area of interest:; absent labels are invisible and unmanaged. Automated tests cover parser validation and boundaries, set/clear combinations, descriptor copying, filtered indices, unrelated-field preservation, JSON compatibility, save/reload after clearing, and UI hiding/wrapping.

Dated interaction notes (US14)

note INDEX d/yyyy-MM-dd [t/TYPE] [o/OUTCOME] n/NOTE appends an interaction note to the person at the displayed client index. It works for clients and prospects, preserves the current filter, and does not replace earlier entries.

Model and command flow

  1. ClientBookParser routes the command to NoteCommandParser. The parser reads the index, date and optional interaction metadata before the first n/, then treats the entire remaining body as text. URLs, slashes and further prefix-like strings remain note content.
  2. InteractionNote stores an immutable LocalDate, nonblank text, InteractionType and InteractionOutcome. Date parsing checks the yyyy-MM-dd shape and uses strict ISO calendar validation. Past dates are allowed. Surrounding text whitespace is stripped; internal content and case are preserved without a character whitelist or maximum length.
  3. NoteCommand checks the displayed index and rejects an exact duplicate in that person's history using InteractionNote.hasSameContent() (date and stripped text) before making changes. Otherwise, it copies the history, appends the new entry and calls Model#setPerson with a replacement Person. Other fields remain unchanged. The same date with different text, or the same text with different dates, is allowed. Person stably sorts its defensive copy by date, oldest first, preserving order for equal dates.
  4. The observable list updates the corresponding PersonListViewCell. LogicManager saves the client book through the existing storage pipeline and returns Added interaction note for NAME. on success.

Person#getInteractionNotes() exposes an immutable defensive copy. History participates in Person equality and hashing, but not duplicate identity detection. Both EditCommand and InfoCommand carry the existing history into their replacement persons. PersonBuilder also preserves it when copying a person.

Persistence and display

JsonAdaptedPerson stores an interactionNotes array of JsonAdaptedInteractionNote objects, each containing date, text, type and outcome. Missing or null arrays in older JSON files become empty histories. Missing or null metadata fields default independently to UNSPECIFIED; unknown or blank stored enum values raise IllegalValueException. Loading validates dates and note text; serialization preserves entry order and duplicates.

PersonCard displays dated, wrapped labels in the existing card's interaction-note container. Empty histories are hidden and unmanaged. Labels have a zero minimum/preferred width and an unbounded maximum width so the parent provides their available width during measurement. Their preferred width must not be bound to the card's actual width: a newly replaced card has not yet been laid out, and that binding causes an excessive first wrapped-height measurement. No fixed card height or forced list refresh is needed.

Validation and scope

The parser distinguishes missing index, date and note prefix; malformed calendar dates and blank text have specific errors. Execution rejects indices outside the currently displayed list before changing the model.

This feature provides adding, displaying, editing and deleting dated notes, with chronological sorting and structured type/outcome metadata. Searching interaction notes (US16) remains outside this feature.

Interaction type and outcome (US15)

InteractionType contains MEETING, CALL, MESSAGE, OTHER, and UNSPECIFIED. InteractionOutcome contains SUCCESSFUL, UNSUCCESSFUL, PENDING, and UNSPECIFIED. The explicit unspecified states represent absent information without inventing historical interaction details. Both the legacy two-argument InteractionNote constructor and old JSON use these defaults. The four-argument constructor rejects null metadata. Full value equality and hashing include both fields, so changes to metadata participate in person equality and persistence; duplicate-note detection deliberately continues to compare only date and text, preserving the existing rule regardless of metadata.

NoteCommandParser retains the date-first syntax and splits at the first whitespace-delimited n/. It tokenizes only the header with PREFIX_DUE_DATE, PREFIX_INTERACTION_TYPE (t/) and PREFIX_INTERACTION_OUTCOME (o/), using the existing ArgumentTokenizer and duplicate-prefix validation. Header whitespace is normalized for tokenization; the body is preserved independently. The optional metadata fields can appear in either order after the date. Enum parsers strip surrounding whitespace and use Locale.ROOT for case-insensitive input, returning field-specific validation errors. The t/ spelling is shared with tags but interpreted only by each command's own parser; find and tag commands retain their existing meaning. Prefix-like strings after n/ remain content, keeping URLs and old note bodies compatible.

NoteCommand still appends through immutable person replacement and the existing LogicManager transaction. JsonAdaptedInteractionNote writes uppercase enum names, accepts case-insensitive stored values, and preserves its two-argument constructor for existing callers. No file migration or dependency is required. Missing/null fields are backward compatible; invalid supplied values are rejected rather than silently discarded. PersonCard already renders each note through InteractionNote.toString(), which now produces DATE [Type: TYPE; Outcome: OUTCOME]: TEXT; wrapping, numbering and chronological ordering are unchanged. NoteEditCommand copies the selected note's metadata when replacing date or text. Deletion removes only the selected note; edit, info, contact preferences, tags and follow-up mutations carry the immutable history through. noteedit does not expose metadata editing; its existing date/text syntax remains unchanged.

Enums were chosen over free text to enforce a small, consistent vocabulary. UNSPECIFIED was chosen over OTHER/PENDING defaults because those values assert details the user may never have recorded. Full value equality is separate from the date/text duplicate rule to avoid both missed persistence changes and duplicate-rule regressions. Keeping metadata before n/, rather than scanning the entire command, protects existing free-form note content.

Tests cover all enum values, mixed-case parsing under a Turkish default locale, independent optional fields, malformed/missing/duplicate prefixes, literal prefixes in the body, explicit defaults, invalid/null values, JSON round-trips and legacy fields. Logic/storage integration tests exercise original filtered indexes, chronological ties, unchanged duplicate rejection, note editing/deletion, unrelated contact mutations, backup/restore and reopening saved records. JavaFX tests assert the exact canonical and unspecified display text.

Editing note date and text

noteedit CONTACT_INDEX NOTE_INDEX [d/DATE] [n/NEW_NOTE_CONTENT] is routed to NoteEditCommandParser. The parser requires two positive indices and at least one editable field. When supplied, the date comes before n/ and is calendar-validated; explicitly supplied future dates are rejected during execution. As with note, everything after n/ is treated as note content, including further prefix-like strings.

NoteEditCommand resolves the contact against the filtered list and the note against its chronologically ordered history, using one-based indices. It rejects out-of-range indices (including empty histories) before mutation. It copies the history and replaces just the selected entry with an InteractionNote containing the supplied date/text (preserving omitted values), original type and original outcome. Date changes trigger chronological reordering. It then calls Model#setPerson with a replacement person preserving all other fields, including contact preferences and the next action. The current filter remains active. LogicManager persists the change through the existing JSON pipeline; no additional schema changes or note IDs are needed for editing.

NoteEditCommandTest and NoteEditCommandParserTest cover validation, filtered lists, duplicate notes, date and contact-field preservation, command routing, and saving/reloading an edit through LogicManager.

Deleting a note

The following sequence diagram shows the successful execution of notedelete 1 2, which deletes the second interaction note from the first contact in the currently filtered list.

notedelete CONTACT_INDEX NOTE_INDEX is routed to NoteDeleteCommandParser, which requires exactly two positive integer indices using ParserUtil.parseIndex.

NoteDeleteCommand resolves the contact against the currently filtered list and the note against that contact's chronologically ordered history. Both indices are one-based. Out-of-range indices, including an empty history, are rejected before changing the model. The command copies the history and removes the selected entry by position, preserving duplicates and the order of remaining entries. Subsequent note positions shift down by one. It calls Model#setPerson with a replacement person preserving all other fields, including contact preferences and the next action, and retains the current filter.

PersonCard prefixes each note label with its one-based chronological position, matching command indices. Replacing the person rebuilds the card through the existing observable list, so remaining notes are renumbered and an empty history is hidden without forcing a refresh or changing stored notes.

Deletion feedback uses the InteractionNote returned by positional removal, including its actual date and text. Only the feedback excerpt has whitespace collapsed. It is limited to 80 Unicode code points using offsetByCodePoints, followed by … when truncated, without splitting surrogate pairs or changing stored content. Command and UI tests cover excerpt boundaries, supplementary Unicode characters, duplicate notes, chronological order, automatic renumbering and hiding the last deleted note's history.

LogicManager saves the replacement through the existing JSON pipeline. No storage schema or model API changes are required. NoteDeleteCommandTest and NoteDeleteCommandParserTest cover validation, filtered lists, duplicate notes, contact-field preservation, command routing, and saving/reloading deletions, including an empty history.

Automated and manual regression checks are described in the Testing guide.

Follow-ups (US18, US19 and US20)

Each Person has zero or one immutable NextAction: an action description, a LocalDate due date, and a boolean completion status. Absence is exposed through Person#getNextAction() as an empty Optional. The value participates in full person equality and hashing, but does not affect duplicate identity detection. Person#withNextAction creates a replacement person while preserving all unrelated information. EditCommand, InfoCommand and NoteCommand must carry this field into their replacement persons.

Recording or replacing an action (US18)

ClientBookParser routes next to NextCommandParser, which uses ArgumentTokenizer for a/ and d/. The parser validates the index through ParserUtil#parseIndex, rejects duplicate prefixes, and distinguishes missing action/date fields. NextAction strips surrounding description whitespace and checks a length of 1–200 Java string characters. Its date parser enforces the four-digit-year/two-digit-month/two-digit-day shape and strict calendar validation. Both parsing and model construction restrict the year to 1–9999; year zero is rejected, including when loading JSON. Calendar parsing and the model continue to accept historical dates so existing saved follow-ups remain loadable as they become overdue.

NextCommand resolves the visible person against its index in the complete list, rejects invalid indices, and checks the requested date against LocalDate.now(clock) before any mutation. Both new and replacement follow-ups must be dated today or later; past dates produce Follow-up date cannot be before today.. The default clock uses Clock.systemDefaultZone(); tests inject a fixed clock to cover today, tomorrow, yesterday, and local-zone boundaries. Validation belongs to the command rather than the date value or storage adapter so previously saved overdue follow-ups continue to load and appear in due. The parser remains responsible for strict date format/calendar validation. The command then passes the replacement person to Model#setPerson. Both new and replacement actions have completed = false. The observable list updates the card. LogicManager then saves through the existing storage pipeline; the command itself does not write files.

Diagram source: NextSequenceDiagram.puml. The diagram shows the successful path, assuming the example date is today or later. Parser failures, invalid displayed indices and past replacement dates stop before mutation; save failures follow the existing LogicManager error handling.

Completing an action (US20)

ClientBookParser routes done INDEX to DoneCommandParser. Empty arguments report Person index is required.; otherwise ParserUtil#parseIndex validates the entire argument string, rejecting zero, negative, non-integer and multiple indices.

DoneCommand first resolves the visible person against its index in the complete list, then checks that the selected person has a next action. These checks occur before any model mutation and report, respectively, Messages.MESSAGE_INVALID_PERSON_DISPLAYED_INDEX and NAME has no next action to complete.. If the action is already completed, the command returns a normal CommandResult with Next action for NAME is already completed. without calling Model#setPerson or changing the filter.

NextAction#markCompleted() returns a new object with the original description and date and completed = true. DoneCommand passes it to Person#withNextAction and calls Model#setPerson, preserving every unrelated person field and the current filter. The card displays Completed through the existing observable-list update. LogicManager saves through the existing JSON storage pipeline and returns Next action for NAME has been marked as completed..

Tests cover the immutable completed copy, preserved description/date and person fields, filtered display indices, out-of-range indices, absent actions, repeated completion, unchanged data on errors, command equality, string representation, parser validation and routing through ClientBookParser.

Rescheduling existing follow-ups (US21)

ClientBookParser routes reschedule INDEX d/yyyy-MM-dd [a/ACTION] to RescheduleCommandParser. It reuses the existing a/ and d/ prefixes, index parsing, NextAction.parseDate and description validation. The parser validates calendar dates and format; RescheduleCommand resolves the client with Command.getVisiblePersonAtIndex, using its original full-list index and rejecting clients hidden by the current filter, as next and done do. It additionally rejects dates before today at execution with Follow-up date cannot be before today.. Its default clock uses the system's local zone, with an injectable Clock for deterministic tests. Duplicate prefixes, missing dates, invalid inputs and past replacement dates fail before model mutation. NextAction.parseDate remains a calendar validator, so existing stored overdue follow-ups remain loadable.

A separate minimal command keeps next creation/replacement semantics unchanged while permitting an omitted description and requiring an existing follow-up. RescheduleCommand resolves the displayed index, rejects a person without a follow-up, then calls NextAction.reschedule and Person.withNextAction before Model#setPerson. The immutable copy always resets completed to false, so rescheduling completed work reopens it. A follow-up rescheduled for today is included when due is run again; a future follow-up remains pending and is excluded until its due date. All other person fields and the active filter are preserved. A due action moved into the future is therefore automatically removed from that filtered view.

LogicManager persists the updated person through the existing JsonAdaptedNextAction; no JSON schema change or migration is required. Parser/command tests cover invalid inputs, displayed indices, missing follow-ups, date-only and description changes, reopening completed actions, rejection of past dates without mutation, local-zone date boundaries and due-filter updates. Model and JSON round-trip tests verify immutable rescheduling, pending status and preservation of optional fields.

Yearly recurring reminders (US22)

ClientBookParser dispatches remind INDEX a/LABEL d/MM-dd to RemindCommandParser, which reuses ParserUtil.parseIndex and the existing action/date prefixes. It rejects duplicate/missing prefixes and constructs an immutable RecurringReminder. Labels are stripped, limited to 50 characters and reject control characters and slashes. The date is a strictly formatted MonthDay; no year or general recurrence rule is stored.

RemindCommand resolves the client through Command.getVisiblePersonAtIndex, retaining the original full-list index after filtering and rejecting hidden clients. It uses Person.withRecurringReminder through Model.setPerson. Case-insensitive label matching updates a reminder in place and retains the existing label's display spelling; otherwise it appends with the supplied spelling. equalsIgnoreCase performs lookup for upserts and deletion, and TreeSet(String.CASE_INSENSITIVE_ORDER) enforces the same equivalence for model and storage uniqueness. This policy is locale-independent and does not lowercase saved labels. Reminder value equality retains display spelling as metadata.

Person defensively copies its reminder list, enforces unique labels ignoring case, and includes it in equality, hashing and every copy path. Existing edit, info and note mutation commands pass the list through their person copies. add syntax and existing constructors are unchanged; older constructors default to an empty list.

JsonAdaptedRecurringReminder stores { "label": "Birthday", "date": "02-29" } within the person's recurringReminders array. JsonAdaptedPerson validates each element and rejects null elements or duplicate labels, including case variants such as Birthday and birthday. A missing, null or empty array loads as an empty list, preserving compatibility with old JSON. Persistence uses the existing LogicManager/storage path, including backup and restore.

ClientBookParser separately dispatches unremind INDEX a/LABEL to UnremindCommandParser, which reuses RecurringReminder.parseLabel for the same label validation as creation. UnremindCommand uses the same getVisiblePersonAtIndex helper, then finds the label ignoring case before any mutation. A missing match (including an empty reminder list) reports a CommandException. Person.withoutRecurringReminder creates an immutable copy without that label and preserves every other field. Model.setPerson re-evaluates the active due filter; removing the last qualifying yearly reminder hides the person unless a due action still qualifies. The existing persistence path saves deletions. remind continues to require a valid nonempty date; its empty date syntax is not overloaded for deletion, consistent with the separate notedelete command.

RecurringReminder.nextOccurrence(today) computes this year's occurrence or next year's if it has passed. MonthDay.atYear maps February 29 to February 28 in non-leap years. NextActionDuePredicate retains its existing incomplete due-action condition and additionally accepts a next occurrence 0–30 days from its captured execution date. The 30-day horizon uses ChronoUnit.DAYS, supports year rollover, and has no accumulated overdue annual occurrence. PersonCard shows labels and next dates in the existing card; done still changes only NextAction.

Viewing due actions (US19)

ClientBookParser routes argument-free due to DueCommand; any arguments are rejected with The due command takes no arguments.. On each execution, DueCommand obtains today's date using LocalDate.now(clock) and calls Model#updateFilteredPersonList with a new NextActionDuePredicate. The predicate includes people with an incomplete next action whose date is today or earlier, or a yearly reminder whose next occurrence is within 30 days inclusive (US22). This replaces any previous search filter without changing stored people. Completing an action through done replaces the person, so the observable filtered list automatically excludes that person unless an upcoming yearly reminder still qualifies.

The default constructor uses Clock.systemDefaultZone(). Tests inject a Clock.fixed with an explicit zone to make the date boundary deterministic. The predicate captures the execution date; rerunning due refreshes it after midnight. Empty results report No follow-ups are due and no yearly reminders are upcoming.; otherwise the command reports the number of matching people, counting a person only once.

The due view is sorted by the earliest qualifying action or yearly-reminder date ascending, then name ignoring case, with exact spelling as a final tie-breaker (#138). ModelManager exposes a SortedList over its existing FilteredList, so sorting does not mutate or persist the backing contact order. The model stores both its current predicate and comparator. LogicManager carries both across its temporary-model execution and successful commit; indexed commands continue to use the displayed client indices from the complete client book, independent of sorted row positions. Replacing a person updates the active order automatically. The original single-argument filter update clears sorting, so list and find retain their original contact-order behaviour. Tests cover date/name ties, stored order, live updates, and indexed commands through the complete logic/storage path.

Persistence and card display

JsonAdaptedPerson stores an optional nextAction object through JsonAdaptedNextAction:

"nextAction": {
  "action": "Send retirement proposal",
  "dueDate": "2026-10-20",
  "completed": false
}

Missing or null nextAction fields load as absence, preserving compatibility with old files. An object with invalid or missing action/date/completion fields is rejected through IllegalValueException. Both pending and completed states survive a JSON round trip.

PersonCard hides and unmanages the follow-up label when absent. Otherwise it displays text and color: completed takes precedence; incomplete dates earlier than today are overdue; remaining actions are pending. The label wraps long descriptions using the available card width. Status is evaluated when a card is constructed; there is no background midnight timer. Restarting the app refreshes all card labels after a date change.

Validation and regression tests

US18 tests cover missing/duplicate prefixes, zero/negative/non-integer/overflow indices, displayed-list bounds, empty and whitespace-only actions, 200/201-character descriptions, trimming, invalid dates (2026-02-30), leap days, rejection of newly scheduled past dates without mutation, today/future acceptance, local clock-zone boundaries, replacement reset, filtered indices, preservation of unrelated fields, old JSON, historical follow-ups remaining visible in due, invalid stored values, completion round trips and card display/wrapping.

Backing up and restoring records

ClientBookParser accepts backup and restore only without arguments and creates a BackupCommand or RestoreCommand respectively. Both commands derive the backup path from the main data-file path, placing clientbook-backup.json beside clientbook.json in the data folder.

BackupCommand does not change the in-memory client book. It serializes the current records through Storage#saveClientBook(ReadOnlyClientBook, Path) to a temporary file in the backup folder, then replaces the backup file with an atomic move when supported. It falls back to a normal replacement move on file systems that do not support atomic moves. This prevents a failed write from replacing an existing backup with a partial file.

RestoreCommand first reads and validates the backup through Storage#readClientBook(Path). Only after a valid ReadOnlyClientBook is available does it save those records to the main data file, replace the temporary model's client book, and reset the active filter to show all persons. It marks the result as already saved so LogicManager does not write the restored records again. A missing, invalid, or unreadable backup leaves the in-memory records unchanged.

Appendix: Requirements

Product scope

Target user profile:

  • maintains one user's local records of clients and prospects
  • stores contact details, relationship status, tags, preferences, interests, important dates, and other concise relationship context
  • records high-level business needs such as financial goals, priorities, budget ranges, and areas of interest
  • records dated interactions, outcomes, next actions, and reminders
  • finds, filters, sorts, reviews, archives, and backs up relationship records
  • supports frequent users who prefer fast typed input while using the interface for clear feedback

Value proposition: Keeps track of their clients' details, allowing them to quickly recall important personal context about their clients, so that they can maintain more personalised and informed client relationships.

Non-Functional Requirements

  1. ClientBook should work on any mainstream OS as long as Java 25 or above is installed.
  2. ClientBook should be able to store at least 1000 persons.
  3. For a data set of up to 1000 persons, ClientBook should process a command and update the graphical user interface within 1 second after the user submits the command.
  4. ClientBook should start within 10 seconds on a computer that meets the stated software requirements.
  5. A user with above-average typing speed for regular English text should be able to complete most core tasks faster using commands than using the mouse.
  6. All core client-record management features should remain available without an Internet connection.
  7. Every successful command that modifies client data should be saved automatically to local storage and remain available after ClientBook is restarted.
  8. An invalid command should not modify any existing client data.
  9. ClientBook should handle a missing, inaccessible, or corrupted data file without crashing or freezing, and should inform the user when recovery is required.
  10. ClientBook should not silently overwrite an unreadable or corrupted data file.
  11. If ClientBook cannot save a change to local storage, it should inform the user that the change may not persist.
  12. ClientBook should store client data locally and should not transmit it to external services.
  13. ClientBook should not require an online account or authentication credentials to access locally stored records.
  14. All core client-record management operations should be accessible using keyboard input.
  15. Error messages should identify the invalid input and provide sufficient information for the user to correct it.
  16. ClientBook should be distributed as a single executable JAR file that does not require a separate installation process.
  17. ClientBook should store its data in a human-readable JSON format to support inspection and manual backup.
  18. The codebase should comply with the project coding standard and pass the configured automated checks before changes are merged.
  19. Unexpected errors should be logged with sufficient diagnostic information for developers while avoiding unnecessary exposure of client information.
  20. ClientBook should support a single user only; its data file should not be accessed concurrently or shared during normal operation.
  21. ClientBook should read and write files only within its home folder (the folder containing the JAR file) and its subfolders, and should not change OS-level configuration settings.
  22. The graphical user interface should work well at resolutions of 1920x1080 and above at 100% and 125% screen scaling, and should remain usable at resolutions of 1280x720 and above at 150% screen scaling.
  23. The distributable JAR file should not exceed 100 MB.

Glossary

  • Mainstream OS: Windows, Linux, Unix, or macOS
  • Prospect: A person who is being tracked as a potential future client but is not currently an active client.
  • Client: A person with whom the financial consultant has an active professional relationship.
