Design

Architecture

The Architecture Diagram given above explains the high-level design of the App.

The following provides a quick overview of the main components and their interactions.

Main components of the architecture

Main (consisting of classes Main and MainApp) is in charge of the app launch and shut down.

  • At app launch, it initializes the other components in the correct sequence, and connects them up with each other.
  • At shut down, it shuts down the other components and invokes cleanup methods where necessary.

The bulk of the app's work is done by the following four components:

  • UI: The UI of the App.
  • Logic: The command executor.
  • Model: Holds the data of the App in memory.
  • Storage: Reads data from, and writes data to, the hard disk.

Commons represents a collection of classes used by multiple other components.

How the architecture components interact with each other

The Sequence Diagram below shows the deletion phase after the user enters delete 1 and confirms with Y.

Each of the four main components (also shown in the diagram above),

  • defines its API in an interface with the same name as the Component.
  • provides its functionality through a concrete {Component Name}Manager class that implements the corresponding API interface.

For example, the Logic component defines its API in Logic.java and implements it in LogicManager.java. Other components interact with a component through its interface rather than its concrete class, preventing them from coupling to that component's implementation, as illustrated in the following partial class diagram.

The sections below give more details of each component.

UI component

The API of this component is specified in Ui.java

The UI consists of a MainWindow and its parts, such as CommandBox, ResultDisplay, PersonListPanel, and StatusBarFooter. All of these, including MainWindow, inherit from the abstract UiPart class, which captures common behavior among classes that represent visible GUI parts.

The UI component uses the JavaFX UI framework. The layouts of these UI parts are defined in matching .fxml files in src/main/resources/view. For example, MainWindow.fxml specifies the layout of MainWindow.

The UI component,

  • executes user commands using the Logic component.
  • displays the exact command submitted by the user above its success or error feedback in the ResultDisplay, wrapping long feedback to the available width.
  • listens for changes to Model data so that the UI can be updated with the modified data.
  • keeps a reference to the Logic component, because the UI relies on the Logic to execute commands.
  • depends on some classes in the Model component because it displays Person objects from the model.

Logic component

API : Logic.java

Here's a (partial) class diagram of the Logic component:

The sequence diagram below illustrates the interactions within the Logic component, taking an add command as an example.

Note: The lifeline for AddCommandParser should end at the destroy marker (X), but due to a limitation of PlantUML, the lifeline continues till the end of diagram.

How the Logic component works:

  1. When Logic is called upon to execute a command, the command is passed to a ClientBookParser object, which in turn creates a parser that matches the command (e.g., AddCommandParser) and uses it to parse the command.
  2. This results in a Command object (more precisely, an object of one of its subclasses e.g., AddCommand) which is executed by the LogicManager.
  3. The command can communicate with the Model when it is executed (e.g. to add a person).
    Note that although this is shown as a single step in the diagram above for simplicity, the code can require several interactions between the command object and the Model to complete the operation.
  4. The result of the command execution is encapsulated as a CommandResult object which is returned from Logic.

LogicManager executes each command against a temporary model initialized with the current records, preferences and active filter. When a command changes records, it saves the temporary client book before committing it to the main model. Read-only commands, such as list, find, and due, update the displayed view from memory without writing to storage. If saving fails, the main model is never committed, so the application does not display a change that would be lost after restart. Regression tests cover read-only commands avoiding persistence, a failed save retaining the records and active filter, and a subsequent successful tag command preserving that filter.

Model component

API : Model.java

The Model component,

  • stores the client book data i.e., all Person objects (which are contained in a UniquePersonList object).
  • stores the Person objects selected by the current filter, such as search results, in a separate filtered list. It exposes this list as an unmodifiable ObservableList<Person> that the UI can observe and bind to, so the UI updates when the list changes.
  • retains the complete list as the source of displayed indexes. Filtering and editing do not change a person's index; deleting a person removes it from the source list and renumbers the persons after it.
  • stores a UserPrefs object that represents the user’s preferences (currently, just the GUI settings). This is exposed to the outside as a ReadOnlyUserPrefs object.
  • does not depend on any of the other three components (as the Model represents data entities of the domain, they should make sense on their own without depending on other components)

Note: The alternative, arguably more object-oriented, design below keeps a unique list of tags in ClientBook, and each Person references tags from that list. This lets ClientBook maintain one Tag object per unique tag instead of each Person holding its own Tag objects.

Storage component

API : Storage.java

The Storage component,

  • can save both client book data and user preference data in JSON format, and read them back into corresponding objects.
  • is implemented by StorageManager, which delegates the actual JSON file access to JsonClientBookStorage and JsonUserPrefsStorage (one class per data file).
  • depends on some classes in the Model component (because the Storage component's job is to save/retrieve objects that belong to the Model)

Common classes

Classes used by multiple components are in the seedu.address.commons package.

Implementation

This section describes some noteworthy details on how certain features are implemented.

Find

The find command supports four independently optional filters: name keywords, one relationship, tag keywords, and remembered-detail keywords. FindCommandParser tokenizes the optional r/, t/, and k/ filters, rejects duplicate prefixes, and requires at least one filter. Name keywords form the preamble and must contain letters with optional internal hyphens or apostrophes, except for the accepted markers s/o, d/o, and w/o. Relationship and tag validation is delegated to ParserUtil; detail keywords accept any non-whitespace text.

The parser creates a PersonMatchesFiltersPredicate. Name keywords use case-insensitive contiguous substring matching and are joined with OR. Thus, Alex matches Alexander, while either Anne or Marie matches Anne-Marie Tan. Tag keywords use the same case-insensitive contiguous substring matching and are also joined with OR; for example, friend matches both friend and friends. Detail keywords search the two contact preferences, the three financial-information fields, each interaction note's date and text, and the follow-up action text and due date. Dates use their ISO yyyy-MM-dd representation, so both full dates and contiguous fragments match. Follow-up completion status, interaction type, and interaction outcome are excluded. Detail keywords are joined with OR. The predicate joins the name, relationship, tag, and detail filter results with AND. For example, find Alex David r/client t/priority referral k/retirement WhatsApp returns clients whose name contains Alex or David, whose tags contain priority or referral, and whose remembered details contain retirement or WhatsApp.

The parsing rules are summarised in the table below:

Filter Matching within the filter
Name Case-insensitive contiguous match against names; any keyword matches.
Relationship Exact Relationship equality.
Tag Case-insensitive contiguous match against tag names; any keyword matches.
Remembered detail Case-insensitive contiguous match against contact preferences, financial fields, interaction-note date/type/outcome/text, or follow-up action/due date; any keyword matches.

The successful CommandResult returned by FindCommand includes a selection request. MainWindow responds by calling PersonListPanel#selectFirstPerson, which selects the first filtered person and scrolls it into view, or clears the selection if the result list is empty. MainWindow enables an explicit find-result navigation state only when that selection request produces a selected person. The state is reset whenever another command is submitted, including an invalid command, so selecting a person with the mouse or executing a non-find command does not activate or retain find-result navigation. While the state is active, a key-event filter on MainWindow handles unmodified Up and Down arrow keys and asks PersonListPanel to select the previous or next result and scroll to that index. Modified arrow keys are left to the focused control. Selection remains at the corresponding boundary when the first or last result is reached. Keeping this navigation at the window level allows it to work while the command box retains keyboard focus.

Tagging a person

TagCommandParser reads the first whitespace-separated argument as the displayed-list index and validates each remaining argument with ParserUtil#parseTag(String). Tag names use the existing alphanumeric-only Tag validation. It retains the parsed values long enough to detect repeated input before collecting them into a set. Because Tag equality is case-insensitive, inputs such as priority PRIORITY raise a ParseException listing the duplicate tags. TagCommand resolves the visible person against its index in the complete list using Command#getVisiblePersonAtIndex. It then intersects the supplied and existing tag sets. A non-empty intersection raises a CommandException listing the tags already on the contact and leaves the contact unchanged. Otherwise, the command unions the supplied and existing tags and replaces the immutable Person through Model#setPerson, preserving every non-tag field and the active list filter. The existing JSON adapter persists a successfully updated set.

AddCommandParser reuses the same tag validation for repeatable t/TAG fields. PersonCard sorts the stored tags before rendering them in its FlowPane. Both commands run on a temporary model, which is saved before its state is committed to the live model.

PersonCard renders the complete tag set in its existing FlowPane, sorting tags alphabetically by name while ignoring case. The list view observes the model, so tags supplied by add or appended by tag appear with the person's contact and relationship details without a manual refresh. The list command restores all persons while retaining those tags.

The following sequence shows tags being appended to a person in the currently displayed list. Parsing and index validation complete before the immutable Person is replaced and the updated client book is saved.

Deleting tags from a person

TagDeleteCommandParser reads the displayed-list index and an optional set of tag names. An empty set means all tags; otherwise, TagDeleteCommand requires every supplied tag to exist on the person. Matching uses the same case-insensitive Tag equality as tag addition. Missing tags, a person with no tags, or an invalid displayed index raises a CommandException before confirmation or mutation.

Tag deletion uses a two-phase Logic flow. The initial Logic#execute(String) call parses and validates the command, stores the pending TagDeleteCommand, and returns a CommandResult containing Are you sure you want to delete this?, the contact name, the exact stored tags that will be removed, and the accepted responses. MainWindow displays the result through the existing result box below the command box.

TagDeleteCommand and DeleteCommand implement ConfirmableCommand, sharing one pending command in LogicManager. Its handleConfirmation method uses the same response rules and invalid-response message for both commands; each command supplies its validation/prompt and cancellation message. Tag deletion's existing prompt, success messages and Tag deletion cancelled. feedback are unchanged.

While a deletion is pending, LogicManager interprets the next command-box input as a confirmation response instead of parsing it as a new command. y and yes execute the stored command; n and no discard it. Matching is case-insensitive and ignores surrounding whitespace. Any other response raises a CommandException and leaves the command pending. A confirmed command copies the person's tag set, clears it or removes the selected tags, replaces the immutable Person through Model#setPerson, and saves the updated client book.

Contact preferences (contact)

ContactCommandParser accepts contact INDEX [ch/CHANNEL|-] [tm/TIMING|-]. It requires a positive index and at least one preference, and rejects duplicate prefixes. Prefixes are case-sensitive and begin after an ordinary space. Other slash-containing text remains part of a value. The parser retains raw arguments so only an exact -, padded with ordinary spaces, means clear. A tab-padded hyphen is normal text and can become a stored - after trimming. PreferredContactChannel and PreferredContactTiming are immutable free-text values with a 1–200 UTF-16-code-unit limit after surrounding whitespace is removed; internal text is preserved. Unpaired UTF-16 surrogates are rejected to prevent replacement characters when saving UTF-8 JSON. The top-level parser preserves raw contact arguments, including Unicode line separators, for preference validation. Invalid values report Preferred contact channel must contain 1 to 200 characters of valid Unicode text. or Preferred contact timing must contain 1 to 200 characters of valid Unicode text., depending on the invalid field.

The parser also performs targeted, case-sensitive malformed-prefix detection after ordinary spaces: /ch and /tm followed by whitespace, /, or the end of input, and the exact prefixes cch/, chh/, ttm/, tmm/ are rejected, including inside values. Index validation comes first, followed by duplicate checks and malformed-prefix detection, so genuinely invalid indices retain their index error. Other slash-containing text, such as Phone/WhatsApp, AM/PM or xx/After 6 pm, remains valid; arbitrary typo detection would incorrectly reject free text.

ContactDescriptor distinguishes three states per preference: omitted (preserve), specified non-null (replace), and specified null (clear). ContactCommand defensively copies the descriptor. It constructs a replacement Person rather than using Person#withContactPreferences, whose null arguments mean preserve and therefore cannot express clearing. All unrelated fields, including recurring reminders and interaction notes with their recorded type and outcome, are copied unchanged.

Command#getVisiblePersonAtIndex first checks the index against the complete person list, selects that person, and then checks membership in the filtered list. It does not interpret the index as a filtered-list position. Thus a sole result labelled 2 requires index 2; index 1 is rejected if that person is hidden.

Both contact and info use the existing LogicManager transaction flow. After parsing, it creates a temporary ModelManager from the live client book and preferences, and applies the current filter and sort comparator. The command replaces the person in this temporary model. If the data changed, LogicManager saves it through Storage before committing the temporary client book, filter and comparator to the live model. Parse or command failures leave the live model untouched; save failures prevent the commit. Unchanged data, including repeated clears, needs no save. The sequence below shows a successful change; individual getters and replacement-person construction are omitted.

JsonAdaptedPerson persists optional preferredContactChannel and preferredContactTiming strings. Missing or null properties load as absent, preserving compatibility with older files; invalid non-null values are rejected. Clearing reuses this absence representation. The card hides absent preferences and wraps recorded values. Parser, command and storage tests cover set/omit/clear combinations, filtered indices, preservation of unrelated fields and save/reload compatibility. InfoContactReleaseAuditTest also checks Unicode line separators through LogicManager.execute, rejection of unpaired surrogates without changing the model or saved JSON, and Unicode preference round trips.

Financial information (info)

InfoCommandParser accepts info INDEX [fn/VALUE|-] [pr/VALUE|-] [ai/VALUE|-], requiring a positive index and at least one field. Prefixes may appear in any order at whitespace boundaries; duplicates, slash-first parameters (including the former /fn, /pr, /ai syntax), and reserved near misses are rejected. Only lowercase fn/, pr/, ai/ are valid. Their case variants and the explicit near misses fnn/, prr/, aii/ (also case-insensitive) produce an invalid-parameter error.

This targeted detection preserves financial notation such as fn/Planning CPF/SRS and fn/Save $3000/month. A generic NAME/ scan is confined to the preamble, where value text cannot occur; the preceding index is validated before reporting an unknown parameter. Inside values, arbitrary forms such as xyz/Value remain text because they are indistinguishable from ordinary slash-containing words. Recognised prefixes always start fields: fn/Review pr/High options sets two fields. There is no quoting or escaping, so users must rephrase literal prefix-like text. The UG documents this restriction and the limited typo detection.

FinancialNeed, Priority and AreaOfInterest are immutable, independently optional values on Person. They accept Unicode letters, combining marks, decimal digits, ordinary spaces and . , ' ( ) & - $ % + /. Validation trims only ordinary spaces, rejects blanks, controls and unsupported characters, and limits each value to 200 UTF-16 code units. No Unicode normalization occurs; combining marks count separately. Priority is free text rather than an enumeration. The parser reports all invalid supplied fields together in financial-need, priority, area-of-interest order, before returning a command.

InfoDescriptor uses specified flags and nullable values to distinguish omission, replacement and clearing, just as the contact descriptor does. Only a raw - surrounded by ordinary spaces clears a field. InfoCommand copies the descriptor, resolves the original full-list index and checks visibility through Command#getVisiblePersonAtIndex, then replaces the person with all unrelated fields preserved. Recurring reminders and interaction-note metadata remain intact. LogicManager uses the same temporary-model, save-before-commit flow described above; the active filter and sort comparator are retained. The sequence below shows priority replacement and area-of-interest clearing in one command.

JsonAdaptedPerson saves optional financialNeed, priority and areaOfInterest strings. Missing or null properties load as absent, while non-null values are validated. Clearing therefore needs no JSON-format change. Present values appear on the card; absent labels are hidden. Regression tests cover financial notation and Unicode, validation and atomicity, descriptor states, original filtered indices, and persistence after setting or clearing.

Interaction notes

note INDEX d/yyyy-MM-dd [t/TYPE] [o/OUTCOME] n/NOTE appends an interaction note to the person at the displayed client index. It works for clients and prospects, preserves the current filter, and does not replace earlier entries.

Model and command flow

  1. ClientBookParser routes the command to NoteCommandParser. The parser reads the index, date and optional interaction metadata before the first n/, then treats the entire remaining body as text. URLs, slashes and further prefix-like strings remain note content.
  2. InteractionNote stores an immutable LocalDate, nonblank text, InteractionType and InteractionOutcome. Date parsing checks the yyyy-MM-dd shape and uses strict ISO calendar validation. Past dates are allowed. Surrounding text whitespace is stripped; internal content and case are preserved without a character whitelist or maximum length.
  3. NoteCommand checks the displayed index and rejects an exact duplicate in that person's history using InteractionNote.hasSameContent() (date and stripped text) before making changes. Otherwise, it copies the history, appends the new entry and calls Model#setPerson with a replacement Person. Other fields remain unchanged. The same date with different text, or the same text with different dates, is allowed. Person stably sorts its defensive copy by date, oldest first, preserving order for equal dates.
  4. The observable list updates the corresponding PersonListViewCell. LogicManager saves the client book through the existing storage pipeline and returns Added interaction note for NAME. on success.

Person#getInteractionNotes() exposes an immutable defensive copy. History participates in Person equality and hashing, but not duplicate identity detection. Both EditCommand and InfoCommand carry the existing history into their replacement persons. PersonBuilder also preserves it when copying a person.

Persistence and display

JsonAdaptedPerson stores an interactionNotes array of JsonAdaptedInteractionNote objects, each containing date, text, type and outcome. Missing or null arrays in older JSON files become empty histories. Missing or null metadata fields default independently to UNSPECIFIED; unknown or blank stored enum values raise IllegalValueException. Loading validates dates and note text; serialization preserves entry order and duplicates.

PersonCard displays dated, wrapped labels in the existing card's interaction-note container. Empty histories are hidden and unmanaged. Labels have a zero minimum/preferred width and an unbounded maximum width so the parent provides their available width during measurement. Their preferred width must not be bound to the card's actual width: a newly replaced card has not yet been laid out, and that binding causes an excessive first wrapped-height measurement. No fixed card height or forced list refresh is needed.

Validation and scope

The parser distinguishes missing index, date and note prefix; malformed calendar dates and blank text have specific errors. Execution rejects indices outside the currently displayed list before changing the model.

Missing indices, dates or note prefixes produce an error. Dates such as 2026-02-30 are rejected with Interaction date must be a valid date in yyyy-MM-dd format. Blank note text produces Interaction note cannot be empty. An index outside the displayed list produces The person index provided is invalid. These input errors leave the stored records unchanged.

Unsupported or empty t/ values report Interaction type must be MEETING, CALL, MESSAGE, OTHER, or UNSPECIFIED. Unsupported or empty o/ values report Interaction outcome must be SUCCESSFUL, UNSUCCESSFUL, PENDING, or UNSPECIFIED. Repeated header prefixes produce the standard duplicate-prefix error. Metadata written after n/ remains literal note text and does not set type or outcome.

This feature provides adding, displaying, editing and deleting dated notes, with chronological sorting and structured type/outcome metadata. Searching interaction notes (US16) remains outside this feature.

Interaction type and outcome

InteractionType contains MEETING, CALL, MESSAGE, OTHER, and UNSPECIFIED. InteractionOutcome contains SUCCESSFUL, UNSUCCESSFUL, PENDING, and UNSPECIFIED. The explicit unspecified states represent absent information without inventing historical interaction details. Both the legacy two-argument InteractionNote constructor and old JSON use these defaults. The four-argument constructor rejects null metadata. Full value equality and hashing include both fields, so changes to metadata participate in person equality and persistence; duplicate-note detection deliberately continues to compare only date and text, preserving the existing rule regardless of metadata.

NoteCommandParser retains the date-first syntax and splits at the first whitespace-delimited n/. It tokenizes only the header with PREFIX_DUE_DATE, PREFIX_INTERACTION_TYPE (t/) and PREFIX_INTERACTION_OUTCOME (o/), using the existing ArgumentTokenizer and duplicate-prefix validation. Header whitespace is normalized for tokenization; the body is preserved independently. The optional metadata fields can appear in either order after the date. Enum parsers strip surrounding whitespace and use Locale.ROOT for case-insensitive input, returning field-specific validation errors. The t/ spelling is shared with tags but interpreted only by each command's own parser; find and tag commands retain their existing meaning. Prefix-like strings after n/ remain content, keeping URLs and old note bodies compatible.

NoteCommand still appends through immutable person replacement and the existing LogicManager transaction. JsonAdaptedInteractionNote writes uppercase enum names, accepts case-insensitive stored values, and preserves its two-argument constructor for existing callers. No file migration or dependency is required. Missing/null fields are backward compatible; invalid supplied values are rejected rather than silently discarded. PersonCard already renders each note through InteractionNote.toString(), which now produces DATE [Type: TYPE; Outcome: OUTCOME]: TEXT; wrapping, numbering and chronological ordering are unchanged. NoteEditCommand copies the selected note's metadata when replacing date or text. Deletion removes only the selected note; edit, info, contact preferences, tags and follow-up mutations carry the immutable history through. noteedit does not expose metadata editing; its existing date/text syntax remains unchanged.

Enums were chosen over free text to enforce a small, consistent vocabulary. UNSPECIFIED was chosen over OTHER/PENDING defaults because those values assert details the user may never have recorded. Full value equality is separate from the date/text duplicate rule to avoid both missed persistence changes and duplicate-rule regressions. Keeping metadata before n/, rather than scanning the entire command, protects existing free-form note content.

Tests cover all enum values, mixed-case parsing under a Turkish default locale, independent optional fields, malformed/missing/duplicate prefixes, literal prefixes in the body, explicit defaults, invalid/null values, JSON round-trips and legacy fields. Logic/storage integration tests exercise original filtered indexes, chronological ties, unchanged duplicate rejection, note editing/deletion, unrelated contact mutations, backup/restore and reopening saved records. JavaFX tests assert the exact canonical and unspecified display text.

Editing note date and text

noteedit CONTACT_INDEX NOTE_INDEX [d/DATE] [n/NEW_NOTE_CONTENT] is routed to NoteEditCommandParser. The parser requires two positive indices and at least one editable field. When supplied, the date comes before n/ and is calendar-validated; explicitly supplied future dates are rejected during execution. As with note, everything after n/ is treated as note content, including further prefix-like strings.

Missing arguments, missing both editable fields, invalid indices, invalid dates, and blank supplied text produce an error without changing records. Invalid dates produce Interaction date must be a valid date in yyyy-MM-dd format. An out-of-range contact index produces The person index provided is invalid. An out-of-range note index, including when the contact has no notes, produces The interaction note index provided is invalid. Blank text produces Interaction note cannot be empty.

NoteEditCommand resolves the contact against the filtered list and the note against its chronologically ordered history, using one-based indices. It rejects out-of-range indices (including empty histories) before mutation. It copies the history and replaces just the selected entry with an InteractionNote containing the supplied date/text (preserving omitted values), original type and original outcome. Date changes trigger chronological reordering. It then calls Model#setPerson with a replacement person preserving all other fields, including contact preferences and the next action. The current filter remains active. LogicManager persists the change through the existing JSON pipeline; no additional schema changes or note IDs are needed for editing.

NoteEditCommandTest and NoteEditCommandParserTest cover validation, filtered lists, duplicate notes, date and contact-field preservation, command routing, and saving/reloading an edit through LogicManager.

Deleting a note

The following sequence diagram shows the successful execution of notedelete 1 2, which deletes the second interaction note from the first contact in the currently filtered list.

notedelete CONTACT_INDEX NOTE_INDEX is routed to NoteDeleteCommandParser, which requires exactly two positive integer indices using ParserUtil.parseIndex.

Missing or extra arguments and invalid indices produce an error without changing records. An out-of-range contact index produces The person index provided is invalid. An out-of-range note index, including when the contact has no notes, produces The interaction note index provided is invalid.

NoteDeleteCommand resolves the contact against the currently filtered list and the note against that contact's chronologically ordered history. Both indices are one-based. Out-of-range indices, including an empty history, are rejected before changing the model. The command copies the history and removes the selected entry by position, preserving duplicates and the order of remaining entries. Subsequent note positions shift down by one. It calls Model#setPerson with a replacement person preserving all other fields, including contact preferences and the next action, and retains the current filter.

PersonCard prefixes each note label with its one-based chronological position, matching command indices. Replacing the person rebuilds the card through the existing observable list, so remaining notes are renumbered and an empty history is hidden without forcing a refresh or changing stored notes.

Deletion feedback uses the InteractionNote returned by positional removal, including its actual date and text. Only the feedback excerpt has whitespace collapsed. It is limited to 80 Unicode code points using offsetByCodePoints, followed by … when truncated, without splitting surrogate pairs or changing stored content. Command and UI tests cover excerpt boundaries, supplementary Unicode characters, duplicate notes, chronological order, automatic renumbering and hiding the last deleted note's history.

LogicManager saves the replacement through the existing JSON pipeline. No storage schema or model API changes are required. NoteDeleteCommandTest and NoteDeleteCommandParserTest cover validation, filtered lists, duplicate notes, contact-field preservation, command routing, and saving/reloading deletions, including an empty history.

Automated and manual regression checks are described in the Testing guide.

Follow-ups

Each Person has zero or one immutable NextAction containing a description, a LocalDate due date and a completion flag. Person#getNextAction() exposes absence as an empty Optional; Person#withNextAction replaces the action while preserving unrelated fields. The value participates in full equality and hashing, but not duplicate identity detection.

All indexed follow-up commands resolve people through Command#getVisiblePersonAtIndex: the index is the original one-based position in the complete client book, and that person must also be visible under the current filter. Filtering and due-date sorting do not renumber contacts. Invalid or hidden indices report The person index provided is invalid.. Rejected commands leave data, the active filter and sorting unchanged.

next and reschedule share description and date validation: descriptions contain 1–200 Java string characters after surrounding whitespace is stripped; dates use exactly yyyy-MM-dd, strict calendar validation and years 0001–9999. At execution, both commands reject a requested date before LocalDate.now(clock) with Follow-up date cannot be before today.. Their default clock uses Clock.systemDefaultZone(); tests inject fixed clocks. Calendar parsing, model construction and storage still accept historical dates so saved follow-ups remain loadable as they become overdue.

The parsers use ParserUtil#parseIndex and ArgumentTokenizer. Space-prefixed a/ and d/ delimit fields in commands that recognise them; they cannot appear literally within an action description. Other text, including URLs, is accepted. Repeated recognised prefixes produce Multiple values specified for the following single-valued field(s): followed by the duplicated prefixes. The error tables below cover command-specific failures; NAME, LABEL and N stand for actual values.

Recording or replacing an action

ClientBookParser routes next INDEX a/ACTION d/yyyy-MM-dd to NextCommandParser. It validates the index, duplicate prefixes, required fields, calendar date and description before constructing NextCommand. The command checks visibility and the execution-date rule above, then calls Model#setPerson with Person#withNextAction. Creation and replacement both set completed = false, including when replacing completed work. Success reports Next action for NAME has been updated successfully..

Validation errors

Blank or overlong action Next action must contain 1 to 200 characters.

Yearly recurring reminders

Viewing due actions

ClientBookParser routes argument-free due to DueCommand. Each execution captures LocalDate.now(clock) and supplies a new NextActionDuePredicate and comparator to Model#updateFilteredPersonList, replacing any previous filter. A person qualifies once if they have an incomplete next action dated today or earlier, or a yearly reminder whose next occurrence falls 0–30 days from the captured date, inclusive. Completed and future one-off actions do not qualify on their own. The default clock uses the system's local zone; rerunning due refreshes the captured date after midnight.

Results sort by the earliest qualifying action or reminder date ascending, so overdue actions come first. Ties use name ignoring case, then exact spelling. ModelManager exposes a SortedList over its FilteredList; sorting changes neither stored contact order nor the original indices used by commands. Replacing a person re-evaluates membership and order. list and find clear the comparator and return to the original contact order.

Nonempty results report N person(s) with due follow-ups or yearly reminders in the next 30 days.; empty results report No follow-ups are due and no yearly reminders are upcoming..

Persistence and card display

LogicManager executes commands on a temporary model carrying the active predicate and comparator. Changed data is saved before the temporary state is committed to the live model; a save failure leaves the live state unchanged. Commands do not write follow-up files themselves.

JsonAdaptedPerson stores optional nextAction through JsonAdaptedNextAction:

"nextAction": {
  "action": "Send retirement proposal",
  "dueDate": "2026-11-02",
  "completed": false
}

Missing or null nextAction loads as absence. Invalid or missing action/date/completion values are rejected through IllegalValueException. Both pending and completed actions survive a JSON round trip. JsonAdaptedRecurringReminder stores each reminder as { "label": "Birthday", "date": "02-29" } in recurringReminders. A missing, null or empty array loads as an empty list; null elements and duplicate labels, including case variants, are rejected. The existing backup/restore path preserves both fields.

PersonCard hides and unmanages absent follow-ups. Otherwise, completed status takes precedence; incomplete dates earlier than today show Overdue, and remaining actions show Pending. Long text wraps. Status and reminder next occurrences are evaluated when a card is constructed; there is no midnight timer. Restarting refreshes all cards after a date change.

Validation and regression tests

Parser and command tests cover missing/duplicate prefixes, index boundaries and hidden contacts, blank/overlong descriptions and labels, strict dates, leap days, local-zone boundaries, past-date rejection, replacement and rescheduling resets, repeated completion, case-insensitive reminder updates/deletion, field preservation and unchanged data on errors. Model, JSON and integration tests cover old files, invalid stored values, round trips, historical overdue actions, the inclusive reminder window and year rollover. DueSortingIntegrationTest verifies date/name ties, original indices, stored order and live membership/order updates through logic and storage. Card tests cover status display and wrapping.

Backing up and restoring records

ClientBookParser accepts backup and restore only without arguments and creates a BackupCommand or RestoreCommand respectively. Both commands derive the backup path from the main data-file path, placing clientbook-backup.json beside clientbook.json in the data folder.

BackupCommand does not change the in-memory client book. It serializes the current records through Storage#saveClientBook(ReadOnlyClientBook, Path) to a temporary file in the backup folder, then replaces the backup file with an atomic move when supported. It falls back to a normal replacement move on file systems that do not support atomic moves. This prevents a failed write from replacing an existing backup with a partial file.

RestoreCommand first reads and validates the backup through Storage#readClientBook(Path). Only after a valid ReadOnlyClientBook is available does it save those records to the main data file, replace the temporary model's client book, and reset the active filter to show all persons. It marks the result as already saved so LogicManager does not write the restored records again. A missing, invalid, or unreadable backup leaves the in-memory records unchanged.

  1. ClientBook should work on any mainstream OS as long as Java 25 or above is installed.
  2. ClientBook should be able to store at least 1000 persons.
  3. For a data set of up to 1000 persons, ClientBook should process a command and update the graphical user interface within 1 second after the user submits the command.
  4. ClientBook should start within 10 seconds on a computer that meets the stated software requirements.
  5. A user with above-average typing speed for regular English text should be able to complete most core tasks faster using commands than using the mouse.
  6. All core client-record management features should remain available without an Internet connection.
  7. Every successful command that modifies client data should be saved automatically to local storage and remain available after ClientBook is restarted.
  8. An invalid command should not modify any existing client data.
  9. ClientBook should handle a missing, inaccessible, or corrupted data file without crashing or freezing, and should inform the user when recovery is required.
  10. ClientBook should not silently overwrite an unreadable or corrupted data file.
  11. If ClientBook cannot save a change to local storage, it should inform the user that the change may not persist.
  12. ClientBook should store client data locally and should not transmit it to external services.
  13. ClientBook should not require an online account or authentication credentials to access locally stored records.
  14. All core client-record management operations should be accessible using keyboard input.
  15. Error messages should identify the invalid input and provide sufficient information for the user to correct it.
  16. ClientBook should be distributed as a single executable JAR file that does not require a separate installation process.
  17. ClientBook should store its data in a human-readable JSON format to support inspection and manual backup.
  18. The codebase should comply with the project coding standard and pass the configured automated checks before changes are merged.
  19. Unexpected errors should be logged with sufficient diagnostic information for developers while avoiding unnecessary exposure of client information.
  20. ClientBook should support a single user only; its data file should not be accessed concurrently or shared during normal operation.
  21. ClientBook should read and write files only within its home folder (the folder containing the JAR file) and its subfolders, and should not change OS-level configuration settings.
  22. The graphical user interface should work well at resolutions of 1920x1080 and above at 100% and 125% screen scaling, and should remain usable at resolutions of 1280x720 and above at 150% screen scaling.
  23. The distributable JAR file should not exceed 100 MB.

Model#deletePerson removes the entire record, including its financial information, contact preferences, tags, interaction notes, next action and yearly reminders. Other records retain their details; remaining full-list indices shift down. The active filter and comparator are retained. LogicManager saves the temporary model before committing it to the live model, so command or save failures leave live data unchanged. Confirmed deletion cannot be undone. Success reports RELATIONSHIP NAME has been deleted successfully., for example Client John Doe has been deleted successfully. or Prospect Jane Tan has been deleted successfully..
